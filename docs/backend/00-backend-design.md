# ConTrack Backend: ประเมินความเป็นไปได้ และแบบระบบ (Multi-tenant + Team + Login)

สถานะ: **ร่างเพื่อขออนุมัติ** (ยังไม่ได้ลงมือทำ) · 2026-10-26

## 1. สรุปสั้น

**ทำได้ และทำได้ไม่ยาก** เพราะการ rebuild วางโครงไว้ถูกทางแล้ว:

| สิ่งที่มีอยู่แล้ว | ทำไมช่วย backend |
|---|---|
| `Project` เก็บ **เฉพาะสิ่งที่ผู้ใช้กรอก** (JSON ขนาดเล็ก หลักสิบ KB) ผลคำนวณสร้างใหม่ทุกครั้ง | เก็บลงฐานข้อมูลได้ตรง ๆ ไม่ต้องเก็บผลลัพธ์ ไม่มีปัญหาข้อมูลคำนวณค้าง |
| `computeProject()` เป็น **pure TypeScript** ไม่ผูกกับหน้าจอ | รันได้ทั้งในเบราว์เซอร์และบนเซิร์ฟเวอร์ (ยอดรวมในรายการโครงการ, ส่งออก PDF/Excel, ตรวจข้อมูล) ด้วยโค้ดชุดเดียวกัน |
| ข้อมูลแบ่งเป็นก้อนตามชีต (`calculators[id]`, `boqOverrides`, `planning.*`, `journey`, `meta`) | ใช้เป็น **หน่วยของการทำงานร่วมกัน**: คนละด่าน = คนละก้อน แก้พร้อมกันได้ไม่ชนกัน |
| store มี action ชัดเจน (`setCalculatorInput`, `setLevelMark`, …) | เปลี่ยนเป็น "เขียนลง server" ได้ทีละ action โดยหน้าจอแทบไม่ต้องแก้ |

ความเสี่ยงหลักไม่ใช่เทคนิค แต่เป็น **การตัดสินใจเชิงธุรกิจ** (ผู้ให้บริการ, วิธีล็อกอิน, รูปแบบราคา) — ดูข้อ 10

## 2. เป้าหมาย (จากเจ้าของระบบ)

1. ขึ้นออนไลน์ มีระบบล็อกอิน
2. บันทึกความคืบหน้าบน cloud (เปิดเครื่องไหนก็ทำต่อได้)
3. ใช้คนเดียวได้ หรือทำงานเป็นทีมบน **BOQ เดียวกัน** ได้
4. **แยก tenant**: แต่ละบริษัทเห็นเฉพาะข้อมูลของตัวเอง

## 3. แนวคิดหลัก: ทุกคนอยู่ใน "Workspace"

ไม่แยกระบบ "บุคคล" กับ "ทีม" — **ทุกอย่างอยู่ใน workspace (= tenant)**:

- สมัครใหม่ → ได้ **workspace ส่วนตัว** อัตโนมัติ (มีสมาชิกคนเดียว) ใช้แบบบุคคลได้ทันที
- บริษัท → สร้าง **workspace บริษัท** แล้วเชิญพนักงาน
- ผู้ใช้หนึ่งคนอยู่ได้หลาย workspace (เช่น ทำงานบริษัท + รับงานส่วนตัว) สลับได้ที่มุมจอ
- โครงการเป็นของ workspace ไม่ใช่ของบุคคล → พนักงานลาออก งานยังอยู่กับบริษัท

```
Workspace (tenant: บริษัท ก. / ส่วนตัวของนาย ข.)
 ├── สมาชิก + บทบาท (owner / admin / estimator / viewer)
 ├── โครงการ A ── ข้อมูลด่าน (ก้อนละชีต) ── revision ที่ออกให้ลูกค้า
 ├── โครงการ B
 └── (อนาคต) ราคากลางของบริษัท, โลโก้/หัวเอกสาร
```

## 4. บทบาทและสิทธิ์

| บทบาท | ทำอะไรได้ |
|---|---|
| **owner** | ทุกอย่าง + ลบ workspace, จัดการแพ็กเกจ/การเงิน |
| **admin** | เชิญ/ลบสมาชิก, ตั้งค่า workspace, ลบโครงการ |
| **estimator** | สร้าง/แก้โครงการ, กรอกด่าน, ออก revision, ส่งออก |
| **viewer** | ดูและส่งออกได้อย่างเดียว (เช่น หัวหน้า, ฝ่ายบัญชี) |

ขั้นถัดไป (ถ้าต้องการ): สิทธิ์รายโครงการ (ให้คนนอกดูได้แค่โครงการเดียว), แชร์ลิงก์ดูอย่างเดียวให้เจ้าของบ้าน

## 5. โครงสร้างข้อมูล (PostgreSQL)

ทุกตารางที่เป็นข้อมูลลูกค้ามี `workspace_id` เพื่อแยก tenant

```
workspaces        id, name, kind('personal'|'company'), plan, logo_url, created_at
profiles          user_id(→auth.users), display_name, phone, line_id
memberships       workspace_id, user_id, role, joined_at            PK(workspace_id,user_id)
invitations       id, workspace_id, email, role, token, expires_at, accepted_at

projects          id, workspace_id, name, start('blank'|'sample'),
                  engine_version('excel-v5'), schema_version,
                  summary jsonb  -- ยอดรวม, % ความคืบหน้า (คำนวณบน server ตอนบันทึก ใช้แสดงรายการ)
                  created_by, updated_at, archived_at

project_docs      project_id, workspace_id, doc_key, data jsonb, version int,
                  updated_by, updated_at                              PK(project_id, doc_key)
                  -- doc_key: 'meta' | 'journey' | 'boq-overrides' | 'calc:<id>' | 'planning:<sheet>'

project_revisions id, project_id, workspace_id, label('Rev 00'), snapshot jsonb (Project ทั้งก้อน),
                  totals jsonb, note, created_by, created_at          -- BOQ ที่ออกให้เจ้าของบ้านแล้ว แก้ไม่ได้

level_assignments project_id, level_id, user_id                     -- (ทีม) มอบหมายด่านให้คน
activity_log      id, workspace_id, project_id, user_id, action, doc_key, at   -- ใครแก้อะไรเมื่อไร
```

ทำไมแยก `project_docs` เป็นก้อน: สองคนแก้คนละด่านพร้อมกันได้โดยไม่ทับกัน, ส่งข้อมูลเฉพาะก้อนที่เปลี่ยน, เก็บประวัติรายก้อนได้

**การแยก tenant**: ใช้ Row Level Security ของ Postgres — นโยบายเดียวทุกตาราง
"`workspace_id` ต้องอยู่ใน workspace ที่ผู้ใช้เป็นสมาชิก" ฐานข้อมูลบังคับเอง แม้โค้ดฝั่งแอปพลาดก็ไม่รั่วข้าม tenant

## 6. การทำงานร่วมกันเป็นทีม

แบ่ง 3 ระดับ เริ่มจากง่ายและพอใช้จริง:

1. **ระดับ 1 — บันทึกอัตโนมัติ + กันทับกัน** (พอสำหรับเริ่ม)
   ทุกก้อนมี `version` เวลาบันทึกส่ง version เดิมไปด้วย ถ้ามีคนแก้ก้อนนั้นก่อน server ปฏิเสธ แอปดึงของใหม่มาแสดง
   "ด่านนี้ถูกแก้โดย คุณสมชาย เมื่อสักครู่" ให้เลือกใช้ของใคร — ไม่มีข้อมูลหายเงียบ ๆ
2. **ระดับ 2 — เห็นกันแบบสด** (แนะนำทำต่อทันที)
   - เปลี่ยนแปลงของคนอื่นเด้งขึ้นจอทันที (realtime) ยอดเงินรวมอัปเดตเอง
   - เห็นว่าใครอยู่ด่านไหน (avatar บนแผนที่ด่าน) + "ล็อกอ่อน": เปิดด่านที่คนอื่นกำลังแก้ จะเตือนก่อน
   - มอบหมายด่านให้คน (เช่น ช่างไฟทำด่านไฟฟ้า, โฟร์แมนทำโครงสร้าง) และดูความคืบหน้าทีม
3. **ระดับ 3 — แก้ด่านเดียวกันพร้อมกันแบบ Google Docs** (ทำเมื่อจำเป็นจริง)
   ใช้ CRDT (เช่น Yjs) รายก้อน — ซับซ้อนกว่ามาก ส่วนใหญ่ BOQ แบ่งงานกันคนละด่านอยู่แล้ว จึงไม่จำเป็นตั้งแต่แรก

## 7. หน้างานเน็ตไม่ดี (offline-first)

ผู้รับเหมามักอยู่หน้างานที่สัญญาณแย่ จึงออกแบบให้ **ทำงานต่อได้ตอนออฟไลน์**:
- store ในเครื่อง (zustand ที่มีอยู่) เป็นสำเนาทำงาน กรอกได้ทันทีไม่ต้องรอเน็ต
- การแก้ไขเข้า "คิวรอส่ง" ส่งขึ้น server เมื่อมีเน็ต แสดงสถานะ "บันทึกแล้ว / รอส่ง 3 รายการ"
- ชนกันตอนกลับมาออนไลน์ → ใช้กลไกข้อ 6.1

## 8. สถาปัตยกรรมที่แนะนำ

```
เบราว์เซอร์ (Next.js เดิม)
  zustand store ── sync layer (คิว + version) ──┐
  computeProject() (เหมือนเดิม)                  │ HTTPS / WebSocket
                                                 ▼
Supabase (Singapore)                 Next.js server (Vercel, region Singapore)
  Auth  : อีเมล, Google, LINE*         route handlers / server actions:
  Postgres + Row Level Security          - สร้างโครงการ, ออก revision, ส่งออก PDF/Excel
  Realtime: เปลี่ยนแปลง + presence      - computeProject() บน server → projects.summary
  Storage : โลโก้, ไฟล์แบบแปลน (อนาคต)   - ตรวจ schema ข้อมูลก่อนบันทึก
```
\* LINE Login สำคัญกับตลาดไทย — Supabase ต่อผ่าน OIDC ได้

**ทำไม Supabase**: ได้ Auth + Postgres + RLS (แยก tenant) + Realtime (ทีม) + Storage ในที่เดียว, มี region สิงคโปร์ (เร็วและเหมาะกับ PDPA), เริ่มฟรี/ถูก, ย้ายออกได้เพราะเป็น Postgres มาตรฐาน
**ทางเลือก**: Neon/RDS Postgres + Auth.js/Clerk + Pusher/Ably — ยืดหยุ่นกว่า แต่ต้องประกอบเองหลายชิ้น ใช้เวลามากกว่า

## 9. เรื่องที่ต้องคิดเผื่อ

- **เวอร์ชันสูตร**: โครงการผูกกับ `engine_version` (ตอนนี้ excel-v5) เมื่อมี Excel v6 โครงการเก่ายังคิดแบบเดิม และมีฟังก์ชันย้ายเวอร์ชันพร้อมรายงานว่ายอดเปลี่ยนเท่าไร
- **Revision ที่ออกให้ลูกค้า**: แช่แข็งทั้งก้อน แก้ไม่ได้ เทียบ Rev 00 กับ Rev 01 ได้ว่าต่างกันตรงไหน
- **ราคากลางของบริษัท** (อนาคต): workspace ตั้งราคาวัสดุ/ค่าแรงของตัวเองทับราคา Excel
- **ความปลอดภัยและ PDPA**: เข้ารหัสระหว่างทาง, RLS, audit log, สำรองข้อมูลรายวัน, ลบบัญชี/ข้อมูลได้ตามคำขอ, ข้อมูลเจ้าของบ้านเป็นข้อมูลส่วนบุคคล
- **ย้ายข้อมูลจากเครื่อง**: ผู้ใช้ที่เล่นในเครื่องอยู่แล้ว ล็อกอินครั้งแรก → "อัปโหลดโครงการในเครื่องขึ้น cloud" หนึ่งคลิก
- **ทดสอบ**: ทดสอบ RLS อัตโนมัติ (ผู้ใช้ tenant A ต้องอ่าน/เขียนของ tenant B ไม่ได้ทุกตาราง) เป็นเงื่อนไขก่อนขึ้นจริง

## 10. สิ่งที่ต้องให้เจ้าของระบบตัดสินใจ

1. ผู้ให้บริการ: **Supabase (แนะนำ)** หรือประกอบเอง
2. วิธีล็อกอิน: อีเมล + Google + **LINE** (แนะนำทั้งสาม) / เบอร์โทร OTP?
3. รูปแบบธุรกิจ: ฟรีสำหรับบุคคล + เก็บเงินรายที่นั่งของทีม? ต้องมีระบบชำระเงิน (Omise/Stripe) ตั้งแต่แรกไหม
4. ทีมต้องแก้ด่านเดียวกันพร้อมกันไหม หรือแบ่งคนละด่านพอ (กำหนดว่าต้องถึงระดับ 3 หรือไม่)
5. ต้องให้เจ้าของบ้าน/ลูกค้าเข้ามาดู BOQ ผ่านลิงก์ไหม
6. โดเมนและชื่อแบรนด์ที่จะขึ้นออนไลน์
