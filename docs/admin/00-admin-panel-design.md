# ConTrack Admin Panel — แบบระบบและแผน MVP

สถานะ: **ร่างเพื่อหารือ** (ยังไม่ลงมือทำ) · 2026-10-26
ขอบเขต: ระบบ BOQ Estimate ปัจจุบัน (32 หมวด + 36 เครื่องคำนวณ + แผนงาน + workspace/ทีม) — ยังไม่รวมเครือข่ายจัดหา/ซับคอนแทรค (`docs/marketplace`)
รูปแบบ: **เรโปใหม่** `contrack-admin` (frontend) + โมดูลใหม่ใน backend เดิม

---

## 0. สรุปใน 1 หน้า

**ความเห็นหลัก:** เห็นด้วยว่าแอดมินต้องตั้ง "วัสดุและราคาตั้งต้น" ได้ และนี่ควรเป็น **ฟีเจอร์แกนของ MVP** ไม่ใช่ของแถม
เพราะตอนนี้ราคาทั้งหมดถูก *generate มาจาก Excel v5 แล้วฝังในโค้ด* การเปลี่ยนราคาปูนหนึ่งตัว = แก้โค้ด + deploy
ซึ่งไม่ใช่งานที่ทีม product/ธุรกิจควรต้องรอ dev

แต่มี **3 เงื่อนไขที่ต้องออกแบบให้ถูกตั้งแต่แรก** ไม่งั้นจะย้อนแก้ยาก:

1. **ราคาเป็น "สมุดราคา" (price book) ที่มีเวอร์ชัน ไม่ใช่การแก้ template สด ๆ** —
   ราคาที่แอดมินเปลี่ยนวันนี้ต้องไม่ทำให้ BOQ ที่ผู้รับเหมาส่งลูกค้าไปเมื่อวานเปลี่ยนยอดเงียบ ๆ
   → โครงการ *ตรึง* เวอร์ชันสมุดราคาไว้ตอนสร้าง และ "อัปเดตราคาเป็นชุดล่าสุด" เป็นการกระทำที่ผู้ใช้เลือกเองพร้อมเห็นส่วนต่าง
2. **ราคาต้องมี key ที่เสถียร** แยกจากโครงสร้าง Excel (`R43`, ข้อความในดรอปดาวน์) —
   ไม่งั้นพอมี Excel v6 หรือเปลี่ยนชื่อรายการ ราคาที่แอดมินตั้งไว้จะหลุด
3. **ลำดับชั้นของราคาต้องชัด**: โครงการ > บริษัท (workspace) > แพลตฟอร์ม (แอดมิน) > Excel v5 ในโค้ด
   MVP ทำแค่ชั้น "แพลตฟอร์ม" แต่ออกแบบ type ให้ชั้น "บริษัท" (ที่ `00-backend-design.md` §9 วางไว้แล้ว) เสียบเข้าได้โดยไม่รื้อ

**MVP ที่แนะนำ (Phase A1):** ล็อกอินแอดมิน · สมุดราคา (ตารางแก้ราคา/ค่าแรง/% เผื่อ ค้นหา กรองตามหมวด) · ร่าง → เผยแพร่ พร้อมเวอร์ชันและประวัติ ·
นำเข้า/ส่งออก Excel · ดูผลกระทบกับบ้านตัวอย่างก่อนเผยแพร่ · รายชื่อผู้ใช้/workspace/โครงการ (อ่านอย่างเดียว + ระงับบัญชี)

**สิ่งที่ MVP ไม่ทำ:** เพิ่ม/ลบ *แถว* ใน BOQ template, แก้สูตร, ราคาเฉพาะบริษัท, แพ็กเกจ/ชำระเงิน, feature flag, ราคาตามภูมิภาค

## 1. สิ่งที่เป็นอยู่: ราคาฝังอยู่ในโค้ด 4 ที่

| ที่ | ไฟล์ | รูปแบบ | ขนาด |
|---|---|---|---|
| **A. BOQ template** | `src/domain/boq/template.v5.ts` (generated) | ทุกแถว item มี `mat`, `lab`, `waste`, `unit` เป็นตัวเลขตรง ๆ (บางแถวเป็นสูตร `consumables` / `linePrice`) | 212 แถว |
| **B. ค่าคงที่ในเครื่องคำนวณ** | `boq/slots.ts` (เหล็ก 25/15, ลวด 50), `piles` (2,500/ต้น), `door-window` (ไม้ 4,000/800, อลูมิเนียม rate), `land-inspection` (ค่าแรง/เดินทาง/ที่พัก) | ค่า default ของ `rebarSlotRows()`, ของ `defaults()`/`blank()` | ~15 ค่า |
| **C. แคตตาล็อกรายการเลือก** | `sanitary-ware`, `sanitary-system`, `electrical-equipment`, `load-center`, `misc` → `*_CATALOGUE: Catalogue` | `{ [ชื่อรายการ]: { unit, mat, lab, note } }` ปิดอยู่ใน `compute()` | ~30 รายการ |
| **D. ค่ามาตรฐานทางวิศวกรรม** | `REBAR_KG_PER_M`, `REBAR_WASTE`, `TIE_WIRE_RATIO`, `EXCAVATION_MARGIN`, `SAND_FACTOR`, ขนาดสาย/ท่อ | ค่าคงที่ | ~20 ค่า |

ชั้นที่ผู้ใช้แก้ได้วันนี้มีชั้นเดียวคือ **รายโครงการ**: `project.boqOverrides[key].mat/lab/waste` และ `PickRow.mat/lab` (null = ใช้แคตตาล็อก)
ระบบแสดง "ไม่มีราคามาตรฐาน ใส่เอง" (`MissingPrices.tsx`) เมื่อแถวมีปริมาณแต่ราคาเป็น 0

**ข้อสังเกตเพิ่ม:** มีไฟล์ `goverment_price.json` (ราคากลางฉลากเขียว ปี 2568, 5,571 รายการ) อยู่ที่ root แต่ยังไม่มีโค้ดใช้ —
เป็นสัญญาณว่าในอนาคตอยากมี "แหล่งราคาอ้างอิง" ซึ่งแบบสมุดราคารองรับได้ (ข้อ 8)

**ข้อเสนอว่าแอดมินควรแก้อะไรได้ใน MVP:** A, B, C ได้ · D **ไม่ให้แก้** (เป็นฟิสิกส์/มาตรฐาน มอก. ไม่ใช่ราคา; แก้ผิดแล้วปริมาณเหล็กผิดทั้งระบบ)
ยกเว้น `REBAR_WASTE` ที่เป็น % เผื่อ → นับเป็นราคา/นโยบาย ให้แก้ได้

## 2. แนวคิดหลัก: สมุดราคา (Price Book) แบบมีชั้นและมีเวอร์ชัน

### 2.1 Price key ที่เสถียร

แต่ละ "สิ่งที่มีราคา" ได้ key เดียว ไม่ผูกกับเลขแถว Excel:

```
boq:R58                      แถว template (MVP ใช้ key เดิม R<row> เป็น id ไปก่อน — มันเสถียรใน v5 อยู่แล้ว)
rebar:DB12                   เหล็กเส้นต่อขนาด (mat/lab) · rebar:tie-wire
pile:standard                ราคาเสาเข็มต่อต้น
door:wood-default            ประตูไม้ default
cat:sanitary-ware:โถส้วม      รายการในแคตตาล็อก (calc id + ชื่อรายการที่ normalize ด้วย matchKey)
```

เมื่อมี Excel v6 ตัว generator จะ map แถวใหม่ → key เดิมด้วยตาราง mapping ไม่ใช่สร้าง key ใหม่

### 2.2 รูปร่างข้อมูล

```ts
// src/domain/pricing/types.ts (ใช้ร่วมกัน frontend + backend)
interface PriceItem {
    key: PriceKey;
    group: string;        // หมวด BOQ (0–31) หรือ 'rebar' | 'pile' | 'catalogue:<calc>'
    label: string;        // ชื่อที่แอดมินเห็น (desc ของแถว / ชื่อรายการ)
    unit: string;
    mat?: number;         // ราคาวัสดุ/หน่วย — undefined = ไม่มีช่องนี้ (แถวที่ราคาเป็นสูตร)
    lab?: number;         // ค่าแรง/หน่วย
    waste?: number;       // % เผื่อ (0.1 = 10 %)
    note?: string;
    source?: 'excel-v5' | 'admin' | 'gov-2568';   // ที่มาของตัวเลข (สำหรับตรวจย้อน)
}

interface PriceBook {
    id: string;
    version: number;      // 1, 2, 3 … เพิ่มทุกครั้งที่เผยแพร่
    label: string;        // "ราคามาตรฐาน ต.ค. 2569"
    publishedAt: string;
    items: Record<PriceKey, PriceItem>;
}
```

### 2.3 ลำดับการ resolve ราคา (ใหม่)

```
ราคาที่ใช้ = boqOverrides / PickRow.mat            (โครงการ — มีอยู่แล้ว)
          ?? workspacePriceBook[key]                (บริษัท — Phase A2)
          ?? platformPriceBook@version[key]         (แอดมิน — MVP)
          ?? template.v5 / ค่าคงที่ในโค้ด            (Excel v5 — fallback เสมอ; golden tests ยังผ่าน)
```

จุดเสียบในโค้ดมีอยู่แล้ว: `computeProject()` รับ `CalcContext` → เพิ่ม `ctx.prices: PriceResolver`;
`computeBoq()` รับ `overrides`/`linked` อยู่แล้ว → เพิ่ม `prices`. `rebarSlotRows(opts)` และ `computePickList(items, catalogue)`
รับราคาเป็นพารามิเตอร์อยู่แล้ว แค่เปลี่ยนจากค่าคงที่เป็นค่าจาก resolver

### 2.4 การตรึงเวอร์ชัน (สำคัญที่สุด)

- `projects.price_book_version` ตั้งตอนสร้างโครงการ = เวอร์ชันที่เผยแพร่ล่าสุดตอนนั้น
- แอดมินเผยแพร่เวอร์ชันใหม่ → **โครงการเดิมไม่เปลี่ยน** แต่ในแอปหลักขึ้นป้าย "มีราคามาตรฐานชุดใหม่ (v7) — ดูส่วนต่าง / อัปเดต"
- "อัปเดต" = แสดงตาราง diff (รายการ, ราคาเดิม → ใหม่, ผลต่อยอดรวม) แล้วเปลี่ยน `price_book_version`; บันทึก activity
- revision ที่ออกให้ลูกค้า (`project_revisions`) เก็บ snapshot อยู่แล้ว ไม่กระทบ
- guest mode (ไม่ล็อกอิน): ใช้สมุดราคาที่ bundle มากับแอป (= เวอร์ชันล่าสุดตอน build) และ fetch ชุดล่าสุดจาก endpoint สาธารณะถ้ามีเน็ต

## 4. บทบาทฝั่งแอดมิน

แยกจากบทบาทใน workspace (owner/admin/estimator/viewer) โดยสิ้นเชิง — คนละตาราง คนละ guard:

| บทบาท | ทำอะไรได้ |
|---|---|
| **superadmin** | ทุกอย่าง รวมถึงแต่งตั้ง/ถอดแอดมินคนอื่น, ลบข้อมูลถาวร |
| **pricing** | แก้ร่างสมุดราคา, นำเข้า/ส่งออก, **เผยแพร่** |
| **support** | ดูทุกอย่าง อ่านอย่างเดียว + ระงับบัญชี + ส่งลิงก์รีเซ็ต |

MVP มี 3 บทบาทนี้พอ; สิทธิ์ละเอียดกว่านี้ค่อยทำเมื่อทีมโตกว่า 5 คน

## 5. สถาปัตยกรรม

```
contrack-admin (เรโปใหม่: Next.js + antd — stack เดียวกับแอปหลัก)
   │  HTTPS เท่านั้น ไม่แตะ DB ตรง ไม่ import domain engine
   ▼
backend (NestJS เดิม) + โมดูลใหม่ 2 ตัว
   modules/pricing     price books, items, publish, preview (ใช้ computeProject() ที่มีอยู่)
   modules/platform    platform_admins, suspend user, admin audit log, สถิติ
   guard ใหม่: PlatformAdminGuard (JWT เดิม + ตรวจ platform_admins)
   routes ใต้ /admin/* ทั้งหมด
   │
   ▼
แอปหลัก: GET /price-books/current (สาธารณะ, cache ได้) + GET /price-books/:version
```

**ทำไมไม่แยก backend:** สมุดราคาต้องถูกอ่านโดย `computeProject()` ทั้งในเบราว์เซอร์และบน server (summary) —
แยก backend = สอง service แตะตารางเดียวกัน ไม่คุ้มใน MVP

**ทำไมแอดมิน frontend ไม่ import `src/domain`:** งานเดียวที่ต้องใช้ engine คือ "พรีวิวผลกระทบ" ซึ่งให้ backend ทำ
(`POST /admin/price-books/:id/preview` → ยอดรวมบ้านตัวอย่างเก่า/ใหม่) เรโปแอดมินจึงบางมาก ไม่ต้อง sync โค้ด domain ข้ามเรโป
ส่วน contract (zod) ใช้วิธีที่ง่ายสุดก่อน: generate OpenAPI จาก backend แล้ว gen client ในเรโปแอดมิน (หรือ copy schema ที่ใช้ 10 กว่าตัว)

**ล็อกอินแอดมิน:** ใช้ identity เดิม (อีเมล/รหัสผ่าน) + ต้องมีแถวใน `platform_admins`; cookie แยก path (`/api/admin/auth`)
ขึ้นจริงควรบังคับ 2FA (TOTP) สำหรับ superadmin/pricing — ใส่ใน A2 ได้ แต่ **rate limit ที่ login ต้องมีตั้งแต่ A1** (ข้อ 41 ใน `OWNER_QUESTIONS.md`)

### 5.1 ตาราง (เพิ่มใน schema เดิม)

```
platform_admins     user_id PK, role('superadmin'|'pricing'|'support'), granted_by, granted_at
users               + suspended_at, suspended_by, suspend_reason          (login ปฏิเสธเมื่อไม่ null)

price_books         id, version int unique, label, status('draft'|'published'|'retired'),
                    base_version int,                 -- ร่างนี้แตกมาจากเวอร์ชันไหน
                    created_by, created_at, published_by, published_at, note
price_book_items    price_book_id, key, group, label, unit, mat numeric, lab numeric, waste numeric,
                    note, source                                           PK(price_book_id, key)
price_book_changes  id, price_book_id, key, field, old, new, changed_by, at   -- ประวัติรายช่อง (ร่าง)

projects            + price_book_version int not null   -- ตรึงตอนสร้าง; migration: ใส่ 1 (= Excel v5) ให้ทุกโครงการเดิม
admin_audit_log     id, admin_user_id, action, target_type, target_id, payload jsonb, at
```

เวอร์ชัน 1 = สมุดราคาที่ generate จาก Excel v5 (A+B+C ในข้อ 1) seed เข้า DB ตอน migrate — เป็นจุดอ้างอิงเดียวกับโค้ด

### 5.2 API ใหม่

| Method | Path | ทำอะไร | บทบาท |

## 6. หน้าจอ MVP (contrack-admin)

1. **เข้าสู่ระบบ** — อีเมล/รหัสผ่าน; ไม่ใช่แอดมิน → "บัญชีนี้ไม่มีสิทธิ์" (ไม่บอกว่ามีบัญชีไหม)
2. **ภาพรวม** — ตัวเลข 4 ช่อง (workspace, ผู้ใช้, โครงการ 7 วัน, โครงการที่ใช้ราคาเวอร์ชันเก่า), ร่างสมุดราคาที่ค้างอยู่, audit ล่าสุด 10 รายการ
3. **สมุดราคา › รายการเวอร์ชัน** — ตาราง: เวอร์ชัน, ชื่อ, สถานะ, เผยแพร่เมื่อ/โดย, จำนวนโครงการที่ใช้; ปุ่ม "สร้างร่างจาก v<n>"
4. **สมุดราคา › แก้ร่าง** — หน้าหลักของ MVP
   - ตารางหนึ่งหน้า: กลุ่ม (หมวด 0–31 / เหล็ก / เสาเข็ม / แคตตาล็อก), รายการ, หน่วย, วัสดุ, ค่าแรง, % เผื่อ, หมายเหตุ; ช่องที่เปลี่ยนจากเวอร์ชันฐานไฮไลต์ + แสดงค่าเดิมจาง ๆ
   - ค้นหาข้อความ, กรองตามกลุ่ม, กรอง "เฉพาะที่เปลี่ยน", "เฉพาะราคา 0"
   - แก้ในตาราง (ใช้ `NumberCell` แบบเดียวกับแอปหลักเพื่อให้พฤติกรรมตัวเลขตรงกัน), undo ต่อช่องจาก changes
   - แถบล่าง: "เปลี่ยน 14 รายการ · บ้านตัวอย่าง 2,145,300 → 2,198,900 (+2.5 %)" กดดูรายหมวด
   - ปุ่ม นำเข้า Excel / ส่งออก Excel / **ตรวจและเผยแพร่**
5. **สมุดราคา › เผยแพร่ (confirm)** — สรุป diff, ผลกระทบบ้านตัวอย่าง, ช่องชื่อเวอร์ชัน + บันทึก, ติ๊กยืนยัน "โครงการเดิมจะไม่เปลี่ยนจนกว่าผู้ใช้กดอัปเดตเอง"
6. **ผู้ใช้ / workspace / โครงการ** — 3 หน้ารายการ ค้นหาได้ คลิกดูรายละเอียด; ผู้ใช้มีปุ่มระงับ/ปลด/ลิงก์รีเซ็ต; โครงการเปิด BOQ อ่านอย่างเดียว (iframe/ลิงก์ไปแอปหลักในโหมด read-only ด้วย token ระยะสั้น — A2; A1 แค่แสดงยอดรวมและ activity)

หลักออกแบบตาม `docs/rebuild/DESIGN_SYSTEM.md`: หน้าเดียวมี primary action เดียว, ภาษาไทยทั้งหมด, ตัวเลขใช้ `NumberCell`

## 8. ความเสี่ยงและข้อควรระวัง

- **แถวราคาเป็นสูตร** (`consumables` x %, `linePrice` ×2): แอดมินแก้ได้แค่ % หรือตัวคูณ ไม่ใช่ตัวเลขตรง — ตารางต้องแสดงให้ต่างชัด
- **แถวที่ Excel ตั้งเป็นเหมา** (ตรวจที่ดิน 7,500, วางผัง 5,500, ตู้ไฟชั่วคราว): เป็นราคาเหมือนกัน อยู่ในสมุดราคาได้เลย — ตอบคำถาม B.3/B.8 ใน `OWNER_QUESTIONS.md` ไปในตัว
- **ราคาในแถวที่ผู้ใช้พิมพ์เอง** (door-window `matPrice` ต่อแถว, ราคาเสาเข็มที่พิมพ์): เป็น input ของโครงการ ไม่ใช่สมุดราคา; สมุดราคาให้แค่ค่า default ตอนเพิ่มแถวใหม่
- **ชื่อรายการแคตตาล็อกเป็น key**: ถ้าแอดมินเปลี่ยนชื่อ "โถส้วม" เป็น "โถสุขภัณฑ์" ต้องเป็นการ *rename key* (มี alias) ไม่ใช่ลบ+เพิ่ม ไม่งั้นโครงการเดิมที่เลือกรายการนี้ไว้จะหลุด — ใน A2 ให้ key ของแคตตาล็อกเป็น id สั้น ๆ แยกจาก label
- **การ generate ซ้ำจาก Excel** (`scripts/excel/gen-boq-template.mjs`): template ยังคงเป็นแหล่งของ *โครงสร้าง* (แถว, สูตร, หน่วย); built-in book เป็นแหล่งของ *ราคา* — ต้องมีเทสต์ว่า key ทุกตัวใน template มีในสมุดราคาและกลับกัน
- **cache**: แอปหลัก cache สมุดราคาต่อเวอร์ชันได้ถาวร (immutable) มีแต่ `current` ที่เปลี่ยน

## 9. คำถามที่ต้องให้เจ้าของระบบตัดสินใจ

1. **ใครคือแอดมิน** — ทีมแพลตฟอร์มเท่านั้น (ตามเอกสารนี้) ใช่ไหม; ส่วน "บริษัทตั้งราคาของตัวเอง" อยู่ในแอปหลักที่ workspace settings (A2) ไม่ใช่แอดมินพาเนล
2. **ราคาใหม่ใช้กับโครงการเดิมอย่างไร** — เสนอ: ไม่เปลี่ยนเอง ผู้ใช้กดอัปเดตพร้อมเห็น diff (ข้อ 2.4) — หรืออยากให้โครงการที่ยังไม่ออก revision เปลี่ยนตามอัตโนมัติ
3. **ค่าวิศวกรรม (กลุ่ม D)** ล็อกไว้ให้ dev แก้เท่านั้นตามที่เสนอ ใช่ไหม
4. **guest mode** ใช้สมุดราคาที่ bundle ตอน build พอไหม หรือต้อง fetch ล่าสุดเสมอ
5. ต้องมี **2FA** ให้แอดมินตั้งแต่ A1 ไหม (เสนอ A2 แต่ถ้าแอดมินมีไม่กี่คนทำใน A1 ก็ไม่ยาก)
6. เรโปแอดมินจะ deploy ที่โดเมนย่อย (`admin.<brand>`) ใช่ไหม — มีผลกับ cookie path และ CORS
